`src/examples/PY/` (py-parser.ts + walker.ts + tocode.ts) + `test/test-py-parser.ts` (19 cases, each round-trips through `Output.toCode` + a `walk()` identity transform + `walkB()`). **tison precedence pitfall (found while adding tocode.ts — affects c-parser.ts too, unfixed there):** the "one `Rules` block + `self` on both operands + `WithPrec(rule, PREC.xxx)`" pattern that c-parser.ts uses produces WRONG trees — everything comes out right-associative and cross-level precedence is inverted (`a - b - c` → `a-(b-c)`, `a | b & c` → `(a|b)&c`). Two compounding causes: (1) `WithPrec` given a `PREC.xxx` *object* (no `level` field) instead of a string key never gets a level, so `reducePrec.level > shiftPrec.level` is `undefined > undefined` = false; (2) when the operator is behind `OneOf([...])` the rule that actually shifts the terminal is the prec-less `OneOf` anon rule, so `shiftPrec` is `undefined` and the shift/reduce conflict falls to the default (shift = right-assoc) regardless. **js-parser.ts's cascade is the pattern that works:** one nonterminal per precedence level, each rule `self OP higher` (right operand is the *level above*, a different nonterminal that can't absorb the next same-level op → left-assoc for free, cross-level precedence purely structural, no `WithPrec` needed). py-parser.ts's expression grammar was rewritten this way in 18441cc; table conflicts 184→4. **c-parser.ts / cpp-parser.ts still have the bug** (their tests only check "doesn't throw" + rough shape) — flagged to the user, left alone as out of scope.

walker.ts: `walk`/`walkB` (mirrors TS/walker.ts, 2 domains only — no Type/declarator), `guard`, `isStmt`/`isExpr`/`isModule`, `calcUnary`/`calcBinary` (Python-faithful: `/` always float, `//` floor, `%` sign-of-divisor, bitwise via BigInt). tocode.ts: `Output` class like the CPP/TS ones but indentation-based suites (no braces/`;`), `elif` reconstruction, f-string/comprehension/slice printers; string `Literal`s re-quote raw text (parser doesn't unescape, so tocode must not re-escape).

**Cross-language AST compatibility (user goal: shared walker/analysis/codegen across C++/TS/Python, eventually "output Python as C"):** as of df2d609 only the FIRST small step is done — py-parser's leaf expr nodes now use `../common`'s `Identifier`/`Literal<T>`/`Unary`/`Binary` (same shapes c-parser.ts + js-parser.ts emit). `and`/`or` → nested `Binary`; chained comparison keeps a Python `Compare` (CPython does too). `True`/`False`/`None` had to fold into the NAME rule's action — an upper-case-initial keyword loses tison's longest-match tie-break to the NAME regex (its `literalPattern` source sorts before `[A-Za-z_]\w*`; lowercase `true` in js-parser wins because `t` > `[`). Reality check surfaced for the user: CPP/walker.ts and TS/walker.ts are fully independent hand-written modules (each has its own copy of `guard()` + its own tag lists), and the `tocode.ts` backends are separate too — there is NO shared generic framework between C++ and TS today, so deeper Python compat = BUILDING that framework. User explicitly deferred the bigger steps (align statement/decl shapes; build a shared generic walker engine; Python→C which needs a whole Python type-inference layer ~backend.ts-sized). ~471+ states, **184 auto-resolved table conflicts** (mostly the permissive one-`Rules`-block expression ladder — shift/reduce left-assoc, reduce/reduce earlier-rule-wins). NB: `parser.tables.conflicts` is only populated on a fresh build; when `makeCachedParser` loads the `.tables-cache/*.tables` it comes back `undefined` (looks like "0") — `rm` the cache before counting.

**Cross-context LALR lookahead pitfall (found twice, root-caused once):** a grammar RULE shared as one object across multiple distinct "outer contexts" gets its reduce's LALR lookahead computed as the UNION of every context's follow-set, not scoped per-context. For `with (a,b):` (see below) this only left a dead precedence hook (no fix found in the time spent). For f-strings it was fully root-caused: `fstring_field` was ONE shared rule reachable from all 4 quote-style contexts, so the state right after its closing `}` had a lookahead set unioning all 4 delimiters' text/close terminals — the lexer, handed that combined `allowed` set, tried all 8 candidates and longest-match picked whichever regex accidentally matched most (a triple-quote text terminal swallowing straight through a single-quote's `"`, since it doesn't exclude that char). **Fix: make the shared sub-rule a factory function called once per context instead of a module-level `const`** — each call produces a distinct rule object, so LALR never unions their follow-sets. Diagnosed by walking `parser.tables.action`/`.goto` directly with a small hand-rolled state-stepper (shift-only; reduces needed manual pop+goto) rather than guessing from parse-error messages — attaching a temporary logging `callback` on the suspect Terminal objects (mutable, exported or found via scanning `tables.action` rows by `.name`) pinpointed the exact match. `optimize:false` does NOT fix or explain this (tested) — it's core LALR construction, not the `eliminateUnitGotos` pass.

Built after the user explicitly rejected a separate tokenise/dedent-injection pass ("no other language created with tison has required a tokenize stage"). The off-side rule lives entirely in the lexer:

- `WS` terminal (in `skip`, spans the newline + trailing blank/comment lines): bracket-depth-aware and blank-line-aware like js-parser.ts's ASI; reclassifies to `NEWLINE` and, against `ctx.indents`, sets `ctx.owedIndent` / `ctx.owedDedents`. **`ctx.indents` is mutated ONLY here.**
- Zero-width `INDENT`/`DEDENT`/`SEP` terminals (`/(?:)/` + callback gate) pay down the debt. Grammar shapes every block body AND the module as `stmt (SEP stmt)*` so these only compete where no real token is valid.
- **Gotcha that ate most of the debugging:** `terminals:[NAME]` (copied from c-parser) injected `{kind:'error'}` NAME entries into every state → NAME (len>0) beat the zero-width tokens. Removed it.
- **Second gotcha:** LALR merges the one-liner-suite path (`suite: simple_stmt`, followed by `elif/else/except/finally`) into the block-internal `simple_stmt` reduce state, so those 4 keywords (length!) out-compete zero-width DEDENT at a block close. Fix: `dedentGuardedKeyword()` — each is a `terminal` whose callback returns `undefined` (rejects its own match) while `ctx.owedDedents > 0`, letting DEDENT take the slot; multi-level dedent-onto-`elif` then attaches to the correct nesting level. Must reference the Terminal objects (ELIF/ELSE/EXCEPT/FINALLY) in rules, never the bare strings, or interning races lose the callback.
- `recover` only fires at EOF (`lex.remaining === ''`): synthesises the final NEWLINE + one DEDENT per open block (lexer loop never runs at offset === length).
- Expression ladder is split `expr_bitor` (CPython `expr`, up to `|`) vs `or_test` (adds comparison/not/and/or) so `for x in xs` targets (`exprlist`, uses `expr_bitor`) don't swallow `in` as the comparison operator.

`with (a as b, c as d):` (3.10 parenthesised form) works. CORRECTION to an earlier claim in this same session: it is NOT resolved via GLR forking — `parser.tables.conflicts` shows 0 live forks anywhere in this grammar (184 entries are all compile-time auto-resolutions). It works because it was never actually ambiguous: once `as` appears only the `with_item` reading can shift it. `with (a, b):` (no `as`, genuinely ambiguous with a tuple) still parses as one tuple, not two managers — tried fixing via `WithPrec` on the colliding rules and via `optimize:false`, neither had any effect (confirmed by rebuilding and re-diffing `tables.conflicts`); walking the actual state tables found no recorded conflict at the `,`/`)` decision point at all, so there's nothing for `WithPrec`/`WithMerge`/`ForceFork` to redirect — whatever makes it deterministic lives inside `buildTables`'s LALR lookahead propagation itself, not reachable from grammar-level annotations. Left as documented behavior; reverted the dead precedence code rather than leave it in.
