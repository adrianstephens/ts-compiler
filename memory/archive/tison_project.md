`tison` is the user's own TypeScript parser-generator library, at `/Volumes/DevSSD/dev/packages/tison`. Analogous to Bison: you pass a plain TS object describing a grammar (terminals carry regex patterns, so tison is the lexer too) and get a parser back. Core engine: `src/tison.ts`. Example grammars: `examples/{js,ts,c,cpp}-parser.ts` (ts/cpp extend js/c via `.push()` onto exported `Rules<T>` arrays). Tests: `test/test-*-parser.ts`.

**Tests must be run via `ts-node`, not `tsc` + `node`.** `test/test-ts-parser.ts` self-parses `src/tison.ts` by reading it via a path relative to `__dirname`; compiling to a custom `outDir` breaks that relative path (the compiled `.js` has no sibling `src/tison.ts`) and the test fails with an unrelated-looking `ENOENT`. Run with `npx ts-node test/test-*.ts` instead of building first.

**`RuleR` (rest-parameter alternative to `Rule()`), added this session:** lets a rule be written as `RuleR(sym1, sym2, ..., action?)` instead of `Rule([sym1, sym2, ...] as const, action)`. Any argument may be an inline `Action`, typed against exactly the arguments before it; the rule's own result defaults to whatever the *last* argument evaluates to. `examples/js-parserR.ts` is the user's in-progress conversion of `js-parser.ts` to this style — as of this session it compiles clean and all test suites pass. Several non-obvious things this ran into, all now fixed in `src/tison.ts`:
- **Type level, T-by-indexing:** deriving the rule's result type `T` by indexing into a union-constrained tuple element (for the last position) breaks under external contextual typing — and *every* real rule in this codebase is written as `Rules<T>(...)` with an explicit `T`, so this bites immediately in practice. Fix: the last position gets its own overload with `T` as an independent free generic (`Action<T, C, ValuesOfR<preceding>>`), not derived via indexing — see the `SymR`/`PlainSymR` overload pairs.
- **Runtime, mid-rule actions saw no values (pre-existing bug, not RuleR-specific):** a mid-rhs function (in `Rule()` too, not just `RuleR`) compiles to a synthetic `anon -> ε { action }` rule with an *empty* `rhs`, so it always ran as `action([], ctx)` — mid-rule actions never actually saw preceding symbol values, regardless of what any type claimed. Fixed by adding `InternalRule.peek`: a count of extra preceding stack values an anon rule's reduce should read (without popping) alongside its own empty rhs. Set from the symbol's index in `resolveSym`.
- **Type level, `PlainSymR` must stay generic:** collapsing `PlainSymR` from a parameterized alias (`PlainSymR<A, C> = Exclude<SymR<A,C>, Action<any,any,any>>`) to a flat non-generic one breaks contextual typing of the trailing action in the sibling same-arity overload — confirmed by direct bisection (swapping just this, nothing else, reproduces/fixes it), root cause in TS's overload resolution not fully understood but empirically load-bearing. Don't "simplify" this away.
- **Type level, `Exclude` over-strips 0-arg thunks:** `Exclude<SymR<A,C>, Action<any,any,any>>` removes more than intended — a 0-arg thunk (`()=>Rules<T>`, from `Forward()`) structurally satisfies `Action<any,any,any>` too (fewer-params-ok function assignability), so `PlainSymR` ends up with no callable members at all, not just no-Action. Harmless for mid-rhs positions (the thunk still gets through via `SymR`'s Action branch's structural leniency and resolves correctly through `ElemValue`'s `(()=>infer U)` case), but breaks `RuleR(Forward<T>(...))` as a *lone* argument (no separate action) — that shape only matched the "sole argument is the action" overload, taking the thunk's return value (`Rules<T>`) as `T` directly instead of resolving one level further. Fixed with a dedicated arity-1 overload `RuleR<T>(s1: () => Rules<T>): Rule<T, any>` tried first — but this in turn had its own trap: it can accidentally swallow a genuine epsilon-action like `RuleR(() => [])`, because an empty array literal infers as `never[]`, which is trivially assignable to `Rules<T>` for unconstrained `T` (giving `T = unknown`). The reliable fix for those call sites is to give the action a dummy param (`(_) => ...`, or `(_: []) => ...` when the arity-1 empty-tuple case still doesn't contextually type `_`) so it no longer has zero declared parameters and doesn't match the thunk-only overload.
- **`WithPrec` (helper added to attach `prec` to a `RuleR()`-built rule, since `RuleR` itself doesn't take a trailing prec arg) — UPDATE, no longer applies:** earlier in this same session `WithPrec(RuleR(...), prec)` inside a `Rules<T>(...)` builder collapsed RuleR's overload resolution unless `WithPrec` was typed with bare `any` instead of `Rule<T, any>`. Re-verified after fixing PlainSymR's genericity and adding the dedicated arity-1 thunk overload (below): `WithPrec<T>(rule: Rule<T, any>, prec: string): Rule<T, any>` now works fine, `$` types correctly through it. Current `src/tison.ts` has it generic again. If this ever regresses, it's almost certainly linked to one of the other two entries below moving back toward their flat/non-generic forms.

**Key architectural fact (non-obvious, cost real debugging effort to establish):** tison's table builder is **SLR(1)**, not LALR(1) or canonical LR(1) — confirmed by `buildTables()` using a single global `follow.get(r.lhs)` per nonterminal for every reduce, not per-state lookahead sets. When a shift/reduce conflict has no precedence info on either side, `setAction()` **silently defaults to shift** and logs it as a `kind:'auto'` conflict. This is the proximate cause of most "wrong parse, no error" bugs found this session — not most flagged 'conflict'/'reduce-reduce' cases, but the *unflagged-feeling* shift-reduce ones that only ever show up as a confusing downstream parse failure. [[tison-debugging-technique]] describes how these were actually found.

**Engine gap found and fixed 2026-07-02: `fork` precedence didn't work for reduce-reduce conflicts, only shift-reduce.** While fixing `binary/src/index.ts` (see `PROGRESS.md` for the full story), found a reduce-reduce conflict between `binding_target -> identifier` and `primary_expression -> identifier` (both in `js-parser.ts`) that was silently resolved by `setAction`'s "earlier rule wins" default — `forceFork`/`assoc:'fork'` (see the `'fork'` assoc feature noted earlier in this memory) had no effect there because `setAction`'s reduce-reduce branch (`src/tison.ts`) never checked for it, only the shift-reduce branch did. Fixed by adding the same fork check to the reduce-reduce branch, then tagging `binding_target -> identifier` with `forceFork`. **If you hit another silently-wrong-parse bug where `tables.conflicts` shows `kind: 'reduce-reduce', resolution: 'reduce by rule N (earlier rule wins)'` and rule N's competing sibling looks like it should win in context, this is now fixable the same way `forceFork` already fixes shift-reduce cases** — just tag one side.

**Second engine gap, same fix session: `defaultMerge` didn't dedup identical GLR-converged values.** Once two GLR paths both survive to the same convergence point (same state+parent) with the *same* resulting value (not just "both valid, different results" — genuinely equal), `defaultMerge` (`src/tison.ts`) used to unconditionally wrap them into a `[left, right]` array regardless, corrupting anything downstream expecting a single value (surfaced as `.map(([, v]) => v)` codegen'ing as two duplicate call arguments). `defaultMerge` now does a `JSON.stringify`-equality check first and collapses to one value when they match, only building an array for genuinely divergent merges. This is a general engine fix, not TS-specific — relevant any time a new `forceFork` tag is added and produces a "both branches parse to the same thing" convergence rather than the usual "one branch dies out downstream" pattern the existing `forceFork` uses (ternary/optional-param) rely on.

**Unit-rule GOTO bypass added to the engine 2026-07-03 (`eliminateUnitGotos` in src/tison.ts, run by `makeParser` unless `spec.optimize === false`):** post-processes the built tables — when goto(s, B) lands on a state whose only possible move is reducing an identity unit rule `A -> B` (default pass-through action, tracked via new `InternalRule.identity` set in `addRule` when no user action was supplied), the entry is redirected to goto(s, A), skipping the no-op reduce round trip. Measured ~1.21x overall (up to 1.45x) on the real-file corpus; 6,284 of 10,418 ts-parser goto entries redirected; ASTs byte-identical opt-on vs opt-off on all 8 corpus files; conflicts untouched (pass runs after conflict collection). CRITICAL constraint baked into the design: only GOTO entries are rewritten, never shift targets, because action rows double as the lexer's allowed-terminal sets (`stream.next(tables.action[state])` after every shift) and candidate-restricted terminal callbacks (regex-vs-divide, WS/ASI, contextual keywords) must see identical rows — don't "extend" this to OneOf-style single-terminal shift states without solving that. Rules with a merge fn are excluded since bypassing would skip their GLR convergence hook. `optimize: false` is the debugging kill-switch if a parse is ever suspected wrong.

**New feature added to address this (unrelated to above):** `Assoc` (in `src/tison.ts`) now includes `'fork'` in addition to `'left'|'right'|'nonassoc'`. A rule tagged with a precedence level whose `assoc` is `'fork'` (via `Rule(rhs, action, 'levelName')` + `precedence: { levelName: 'fork' }` in the `GrammarSpec`) forces its shift/reduce conflicts to resolve via GLR (`kind:'conflict'`) even when the *other* side of the conflict has no precedence at all — unlike `'nonassoc'`, which only forces GLR when both sides already have matching-level precedence. Use this on a rule you know is genuinely, irreducibly ambiguous (can't be disambiguated by one token of lookahead) rather than accepting the silent-shift default. Applied to `examples/ts-parser.ts`'s `parameter`'s bare `IDENT '?'` rule (optional-parameter marker) to resolve its conflict with `conditional_expression`'s ternary `?` — they're genuinely ambiguous one token in (`(a ? ...` could be a parenthesized ternary or `(a?) => ...` an arrow with an optional param), and only resolve once you see whether `=>` follows the matching `)`, arbitrarily far ahead — the canonical case for needing GLR, not a stronger grammar class. (Mid-fix when this memory was written — verify against current source before relying on the specific rule names.)

**Foundational lexer bug found and fixed 2026-07-03: `lex.prev` was ALWAYS `undefined` in every terminal's `lex` callback, engine-wide, since day one of this mechanism.** `nextToken` (src/tison.ts) built each callback's context object with `prev: state.lastShifted` — but nothing anywhere in the file ever set `.lastShifted`; only `.prev` gets set on the actual stream object (`stream.prev = realTok`, in two places). Since `state` passed into `nextToken` **is** that same stream object (already carrying a correct `.prev` via `Lexer`'s own declared field), the explicit `prev: state.lastShifted` line was overriding the spread's already-correct `.prev` with `undefined` every single time. Fix: changed `nextToken`'s own mismatched inline parameter type (`{ lastShifted?: Token }`) to `{ prev?: Token }` and deleted the erroneous override line entirely (the `...state` spread already carries the right value through). This one-line bug silently disabled: (1) `RESTRICTED_AFTER`/`RESTRICTED_BEFORE_PREV` ASI checks in js-parser.ts's `WS` terminal (confirmed root cause of `test-js-parser.ts`'s "ASI: restricted production (postfix ++)" failure — `a\n++b` was shifting `++` onto `a` as a genuine postfix continuation instead of inserting `;`); (2) `REGEX_LITERAL`'s `regexDisallowedAfter` rejection (turned out low real-world impact — the candidate-restriction design already keeps REGEX_LITERAL out of most division-position states' allowed sets, confirmed via an A/B test reconstructing the exact pre-fix code: `a / b / c` parsed identically both ways); (3) `jsRecover`'s `newlineBefore` check (recovery-based ASI still partially worked via its other two conditions, `remaining.startsWith('}')`/`!remaining`). After the fix: all 4 fast suites pass with ZERO failures, including the ASI test for the first time this session. Corpus round-trip count (`test-ts-parser.ts`) unchanged at 71 (neither this nor the method_signature fix below happened to be the root cause of any of the known 71 — expected, both are narrow edge cases, but worth confirming no regression).

**Second grammar gap found and fixed 2026-07-03: a bodyless class `method_signature` (overload signature, e.g. `bar(x: number): void;` inside a class) failed to parse EVEN STANDALONE, with no sibling method and no modifier.** Root cause (found via table inspection, not guessing, per [[tison_debugging_technique]]): `class_member_overloads` (the Rules array holding all 4 method_signature alternatives) was reachable from `tsClassMember` (ts-parser.ts) ONLY via `Rule([class_member_modifier_list, class_member_overloads])` — and `class_member_modifier_list` is built from `List(OneOf([...]))` with no separator, which per `List`'s own implementation always requires >=1 item (never nullable). So a method_signature with zero modifiers (the common case) had no path into the grammar at all. Compare to the sibling, working case: `class_member_body` gets a modifier-less path for free because js-parser.ts's own base `class_member` already spreads `class_member_body` in directly as one of its alternatives — no equivalent bare alternative existed for `class_member_overloads`. Fixed by adding `...class_member_overloads` (spread directly, mirroring js-parser.ts's own pattern) as one more alternative on `tsClassMember.push(...)`. Verified: conflict-table counts unchanged (57 js / 3055 ts, matching the pre-fix baseline exactly) — confirms no new ambiguity introduced, just a previously-unreachable production made reachable. This also unblocks testing `method_signature`-erasure logic in ts-codegen.ts's `TStoJS`/`isErasedClassMember`, which was previously untestable via any real parse (see [[tison_codegen]]).

**Third grammar gap, 2026-07-03/04: `static load(): void;` (sole `static` modifier + bodyless method_signature) still failed even after the fix above (which only covered the zero-modifier case).** This was the hardest bug of the `TStoDecl` session — see [[tison_debugging_technique]]'s "fourth class" entry for the full two-wrong-hypotheses-then-right-fix story (a dedicated lookahead terminal and a `forceFork` tag were each tried and empirically proven to have zero effect, because `tables.conflicts` had no entries at all for the relevant rules — this was a missing-transition bug from LR(0) state-merging, not a resolvable conflict, so `forceFork` structurally could not have helped). Root cause: js-parser.ts's own `Rule(['static', class_member_body])` shifts `static` directly and only ever completes for field/bodied-method shapes; reaching `class_member_overloads` needed an intermediate `class_member_modifier_list` reduction that the shift-preferring SLR default never backs off to take. Fix: added `Rule(['static', class_member_overloads], $ => ({...$[1], modifiers: ['static']}))` in ts-parser.ts (right after the existing modifier-list rule, extensively commented with the root cause and both reverted wrong hypotheses) — gives `static` its own direct, symmetrical path to `class_member_overloads`, paralleling js-parser.ts's existing direct path to `class_member_body`. Verified with 11 targeted repros (all pass) plus zero new conflicts recorded for the new rule.

**cpp-parser.ts extended to (approximate) C++14, 2026-07-04.** `examples/cpp-parser.ts` was rewritten from "C plus classes/templates demo" to broad C++14 coverage (see its header comment for the feature list and honest omissions). `test/test-cpp-parser.ts` now has 15 verbose AST-dump tests + 111 compact pass/fail coverage checks, all green; c/js/ts/tison suites unaffected. Non-obvious mechanisms worth knowing before touching it again:
- **Tables are built eagerly at `makeParser()` (module top level of c-parser.ts), so cpp-parser may freely `splice`/replace shared C rules, not just `.push`** — used to delete C's legacy `auto` storage class (freeing `auto` to be a real type_specifier, which makes generic lambdas/`auto f()`/`auto&` all fall out of C's declaration machinery for free), C's monolithic named struct/union/enum rules (replaced by eager-registering heads), and C's bare-`[IDENT]` struct_declarator.
- **TYPE_SCOPE lexer hack:** IDENT's shared callback was extended (gated on `ctx.templateDepth !== undefined` so plain cParser is untouched at runtime despite the shared Terminal object) — a registered name followed by `::` lexes as `TYPE_SCOPE`, not `TYPE_NAME`. This makes qualified-expression vs qualified-type vs out-of-class-definition disambiguation lexical instead of an unresolvable reduce-reduce; namespace/class/enum/alias names all register eagerly (head rules reduce before `{`).
- **Scoped/qualified types must be `specifier_qualifier_list` STARTERS, not type_specifier alternatives** — on type_specifier their TYPE_SCOPE shift lives in spec_qual's extension state and beats the declaration_specifiers reduce that `int Foo::getX()` needs, absorbing `Foo::` as a second type specifier.
- **Never spell overlapping keywords as both a `termOneOf` group and standalone literals reachable in the same state** — the lexer tie-breaks equal-length matches by pattern source, starving one grammar path entirely (a `static|virtual|...` member-modifier terminal silently ate the `virtual ~dtor` path). Modifier lists are a Rules nonterminal over individual literals instead.
- **Don't route a "name directly followed by `(`" construct through a shared one-token nonterminal (type_ident)** — ctor rules inline raw `TYPE_NAME '(' ...` so the choice vs type_specifier is an ordinary shift/reduce; via type_ident it's a reduce-reduce whose earlier-rule-wins resolution flips with rule *traversal* order (it did flip during the rewrite, breaking every TYPE_NAME-typed member).
- **Non-type template params use a restricted simple-type nonterminal, not spec_qual** — full spec_qual drags struct/class head items into the template-param state and creates a `class T`-vs-class_head reduce-reduce on `>`/`,`.
- C gaps fixed en route (in cpp-parser only, C grammar untouched): leading cv-qualifiers (`const char*`), zero-arg calls `g()`, empty for-clauses `for(;;)`, cv-qualified pointer levels, unnamed (abstract-declarator) parameters.

**Bareword-keyword-vs-identifier leak pattern, root-caused 2026-07-09 with actual table/state dumps (not guessing) — a real, reusable debugging story for [[tison_debugging_technique]].** Symptom: `ts-codegen.ts`'s own local variable named `global` (`global.values.set(...)`, inside an ordinary function body, nothing to do with `declare`) failed to parse ("stuck in error recovery... 'global'"), even though `global` the *keyword* is only grammatically reachable through `declare module {...}`/`namespace {...}`/`declare global {...}` bodies (`declared_body_item -> Forward(() => declare)`, and `declare` includes `Rule(['global', '{', declared_body, '}'])`). The natural assumption — "SLR/LALR state-merging must be leaking an unrelated state's items into this one" — was **wrong**; verified by dumping the actual LR(0) item cores (`tables.lr0States`, instrumented via a throwaway copy of `src/tison.ts` re-exporting it) for the specific states hit during a real parse trace. The *actual* mechanism: `JS.variable_decl_statement` (`const x = 1;`) is reused as **one of `declare`'s own alternatives** (ambient bodies don't repeat the `declare` keyword per-item), so the single LR(0) state reached right after that production's trailing `;` is **structurally the same state** regardless of which context reached it (LR states are built purely from the rule+dot core, with no memory of caller) — its lookahead set is therefore the *union* of "what can follow an ordinary statement" and "what can follow a declared_body_item", which legitimately includes bare `global`. That widened lookahead is normal/harmless LALR behavior on its own (real per-state lookahead still narrows things in most cases) — it only became an actual bug because `global`, unlike `readonly` (which already has a lookahead-disambiguating `terminal(name, pattern, lex)` callback), had **no fallback**: once the lexer saw `global` was a "legal" candidate there, `term.callback` being absent meant it committed to the `GLOBAL` token unconditionally, with no chance to reconsider as `IDENT`. Fix (mirrors `READONLY`'s existing pattern exactly): `const GLOBAL = terminal('global', /global(?!\w)/, lex => /^\s*\{/.test(lex.remaining) ? GLOBAL : IDENT);` — only the keyword when immediately followed by `{`. **General lesson: any bareword keyword terminal in `ts-parser.ts` that is also a nonterminal-shared-across-contexts risk (i.e., used inside `declare`'s alternatives, which is itself spliced into multiple call sites) needs the same disambiguating-callback treatment as `READONLY`/`GLOBAL`, or it's a latent bug waiting for a real identifier to collide.** `namespace`/`module` share this exact risk and are NOT yet fixed (no known failure hit yet, just flagged).
