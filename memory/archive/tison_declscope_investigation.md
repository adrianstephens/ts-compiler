**Goal:** `resolve()`'s `'ref'` case in `type-utils.ts` deliberately does NOT consult a ref's own `t.declScope` (its declaring scope) — only `lookupMember`/`hoistVar` do, in bounded ways. Fully enabling it in `resolve()` is what fixes font.ts/woff.ts's DOM-`Element`-vs-`xml.Element` false positives (and others), but every prior attempt (3+ times before this session) destabilized self-hosted checking and got reverted, with the exact mechanism undiagnosed.

**Root cause found this session (2026-07-21/22), confirmed empirically via instrumented `stampScope`:** `NodeModules` (module-loader.ts) caches every lib/`node_modules`/workspace-package AST at *process* lifetime (`static found`/`imported` maps), but `ts-codegen.ts` used to rebuild a *fresh* `Scope` per `TStypeCheckAsync` call and re-hoist that same shared AST into it each time. `stampScope` mutates refs in place and skips a ref that's already tagged, so whichever file got checked first permanently claimed `declScope` on every such ref for the rest of the process — every later file's own refs into that package pointed at an orphaned `Scope` belonging to an unrelated earlier file. Measured: 87 cross-scope stamp collisions on `Element` alone from checking just 2 files back to back.

**Fixes landed this session, all verified zero-regression on the full corpus with `declScope` still off, and independently confirmed to help when temporarily re-enabled:**
1. **`getLibScope`** (ts-codegen.ts) — builds the lib-derived `Scope` once per process (keyed by `libSpecs`), reused for every file instead of rebuilt+re-stamped per file.
2. **`resolveImport`'s scope-leak fix** — was threading the *importer's* own local scope as the built dependency's ambient parent instead of `global` (inconsistent with how re-exports already used `global` correctly). Fixed and simplified (`awaitScope`/`makeScope` dropped the now-always-`global` `parent` param entirely).
3. **`importScopeCache`/`waitingFor` promoted to process-wide**, matching `getLibScope`'s pattern — plus **`ModuleShape.tainted` tracking**: Node's own `fs`/`fs/promises`/`node:fs`/`node:fs/promises` `.d.ts` graph has a *genuine* 4-hop circular re-export. `wouldDeadlock`'s cycle detection correctly truncates one side of a genuine cycle (by design, pre-existing) — but sharing the wait-graph process-wide means *entry order from whichever file gets there first* permanently decides which side comes back hollow, for every file afterward. `tainted` propagates through everything that awaited a truncated part; `makeScope` evicts (but doesn't retroactively invalidate) a tainted build from the cache once known, so the next fresh top-level entry point gets its own honest attempt instead of inheriting a poisoned one forever. Root-caused via a real-corpus trace (not guessing) showing `binary/test/test.ts` entering the cycle from a different angle than isolated single-file repros, truncating `fs`'s own `promises` re-export specifically.
4. **`isAssignable`'s union-ordering bug** (`recurse`'s `dst.type === 'union'` case) — when `dst` is a union but `src` doesn't look like one yet (still a bare unresolved ref), the dst-union rule narrows `dst` to one candidate *before* `src` gets resolved, so a union hiding inside `src` (behind an intersection, `(A|B) & C`) only ever gets checked against that one narrowed candidate, never the full `dst`. Fixed additively: once the narrowed attempt fails and `src` is an intersection, also try its parts against the *full* unnarrowed `dst` union. Root-caused via a minimal isolated repro (`@isopodlabs/binary`'s `interop.stream(file0)` return type vs `bin._stream | bin.async._stream`) plus targeted `console.error` tracing inside `recurse` itself (temporary, removed after).

**All three follow-on gaps fixed (2026-07-22), `declScope` confirmed stable and left enabled — investigation complete:**
- `binary-ml/onnx.ts:280/287` — fixed: `typeOf`'s `'function'`/`'arrow'` case was letting `checkFunctionBody`'s internal inference overwrite `fn.returnType` even when the function had an explicit declared return type. Captured the declared type before the call and threaded it through a new `FixSig` 3rd param (`declaredReturnType`) that takes priority.
- `maths/factors.ts:362/374` — two stacked root causes: (1) `exportScope`'s identifier-expression default-export handling (`export default rational`) only copied the value, never a coexisting same-named type, via `scope.copy` instead of manual value-only `addValue`; (2) `inferTypeArgs`'s `function`/`constructor` case required `a.type === paramT.type` exactly, but an `Object.assign`-built callable value (e.g. `rational`) resolves to an `'intersection'` — fixed by reusing `flattenIntersection` to find the actual callable part first. Net corpus effect: 17→13 errors, fixed 4 files including a bonus (`symbolic.ts:341`).
- `symbolic/tests/test-sym.ts:702` — root cause was one level up from the other two: explicit type arguments at a *call expression* (`Polynomial<symbolic>(...)`, TS 4.7 `expr<T>` instantiation syntax) are raw AST, read straight off `e.typeArgs` in `checker.ts`'s `'call'`/`'new'`/`'instantiation'` cases — never `stampScope`d the way a declaration's own annotations are. Once such a ref got substituted into the callee's generic body (`realRoot<T>` in polynomial.ts) and needed resolving from the *callee's* declaring scope, the bare `symbolic` ref (no declScope) was unresolvable there, `isAbstract` wrongly returned true, and the conditional's `combineTypes([trueType,falseType])` fallback produced a bogus `number | conditional` union. Fixed by stamping `e.typeArgs` with the call-site `scope` at both read sites before use. Confirmed via A/B: 14→13 errors, exactly `test-sym.ts:702` gone, nothing else moved.

All three were separate, real, pre-existing checker gaps that were also being masked by the same "unresolved ref: lenient" leniency the union-ordering bug was hiding behind — not more instances of any single fixed bug, as suspected.

**Final verification (2026-07-22):** full corpus 13 ERROR / 539 GAP (down from the pre-declScope-work baseline), all 3 fast suites (test-tison.ts, test-js-parser.ts, test-c-parser.ts) exit 0 clean, eslint 0 errors (only pre-existing/accepted warnings). `declScope` consultation in `resolve()`'s `'ref'` case stays enabled permanently — this investigation is closed.

**A 5th, later, related-but-distinct `declScope` bug found (2026-08-20/21), see [[tison_towasm_self_hosting_plan]] for full detail — this file's own "closed" status is unaffected, different mechanism.** `stampSig` (used by `hoist()`'s pre-pass for nested function declarations) stamped a hoisted function's *entire* signature — including references to its own type parameters — with the *enclosing* scope, before the function got its own body-check scope; `declScope`'s set-once semantics then permanently shadowed a nested function's own same-named type param with the outer function's. Not `resolve()`'s ref-case consultation (this file's original subject) — a premature-stamping-during-hoisting bug, exposed only once `checkFunctionBody` started registering function type parameters for real (previously either scope's lookup of an unregistered name gave the same "not found" answer, so which one you asked never mattered). Same "leniency was masking a real bug" pattern as this file's own follow-on gaps.

**A 6th, separate `??=`-first-wins scope-stamping fragility, CLOSED (2026-08-21), see [[tison_towasm_self_hosting_plan]] for full detail.** Not `declScope` itself, but the same *class* of bug: `checkFunctionBody`'s `fn.scope ??=` / `checkStmt`'s `(stmt as any).scope ??=` (towasm.ts's own narrowing-aware-scope channel, unrelated to the checker's `declScope`) had a known, previously-reverted trade-off — `makeLibScope()`'s one-time muted check either stamped every lib method (fixing `String.split`'s narrowing) or stamped none (needed so a generic class's shared method template, e.g. `Map<K,V>.entries()`, didn't get its unresolved-`T` scope permanently frozen ahead of any real instantiation). Root fix: stop conflating "walk the body" with "stamp the scope" — added `Scope.isGenericTemplate()`, and `checkFunctionBody` now always walks (so side effects like `applyContextualParams` still run) but only *stamps* when the walk isn't both muted-with-a-declared-return-type *and* under a generic class's own instance scope. The precise gate mattered: a first cut gated purely on `scope.isGenericTemplate()` and broke `Array<T>`'s own constructor (checked under the same generic-flagged scope but never actually part of the risky case, since `skipReturn` always forces its `expected` false) — fixed by computing the narrow condition once (`noStamp = !!expected && !err && scope.isGenericTemplate()`) and threading it explicitly rather than re-deriving it from the scope alone at each stamping site.
