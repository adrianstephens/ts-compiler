Started from user report: "optional arguments not supported (numFill test fails)" in [[tison_towasm]]. Root-caused and fixed three bugs by following the failure chain forward (each fix let the test script run further and exposed the next one) — see [[feedback_fix_forward_not_revert]]. Then hit a fourth, architecturally deeper issue and stopped to check with the user rather than continue unilaterally.

## Fixed

1. **Optional-arg pattern unsupported by design, not just missing** — `examples/TS/lib/array.ts`'s `slice`/`fill`/`copyWithin` used `param?: number` + runtime `=== undefined`/`??=` sensing. towasm.ts's design can't support that: numbers can't be nullable (no boxing), and call-site default-filling (`fillDefaultArgs`) only accepts plain literal defaults, never runtime-evaluated ones. Fixed by rewriting all three to real literal defaults (`= 0`, and a large literal sentinel `9007199254740991` for "omitted end", clamped down to `len` — this also happens to match real JS's own end-clamping spec behavior). Also fixed a real correctness bug found along the way: `fill`'s loop ignored `start`/`end` entirely and always filled the whole array.
2. **Unary negation stack-order bug** (`examples/TS/towasm.ts`, `builtins['prefix-']`) — `-x` for i32/i64 compiled as `[operand, const(0), sub]` = `operand - 0`, not `0 - operand`, because the operand is pushed *before* an operator's `inline` instructions run (see `emitExpr`'s `'unary'` case) — the code wrongly assumed `const(0)` would be pushed first. So `-1` evaluated to `1`. This silently broke every `!== -1` sentinel check and `?? null`/optional-chaining pattern in the whole test suite (fixing it turned `fieldNull`/`callNull`/`arrBoolMethods` green as a side effect, previously misdiagnosed as array-specific bugs). Fixed by switching i32/i64 to `[const(-1), mul]` (commutative, stack-order-independent); f64 already used the safe unary `f64.neg` and was never affected.
3. **Typed-array `.length` silently resolves to `any`** (`examples/TS/checker.ts`, `typeOf`'s `case 'member'`) — `Uint8Array`/`Int32Array`/`Uint32Array` have no backing class/interface declaration anywhere in the checker's type universe; only `case 'index'` (element access) special-cased them, never plain member access. So `this.length` inside a Uint8Array-instantiated `Array<T>` method resolved to `any`, and towasm.ts's `emitStmt` threw `local 'len' has an unsupported type` trying to give it a wasm type. Added the same `TYPED_ARRAYS.has(name)` special case to the member-access path, returning `T.NUMBER` for `.length`.

## Session continued same day: emitExpr return-type question, then the div/0 fix + Uint8Array range-typing

User asked to verify whether `emitExpr`'s `WasmType` return value is still needed (suspected it's now derivable via `wtypeOf`/checker inference alone). Verified it's NOT redundant, with two concrete counter-examples: (1) `Uint8Array` element reads physically produce `i32` (`array.get_u`) but logically type as `number`/f64 — `emitExpr` returns the true physical type so `coerceTop` knows a conversion is still owed; (2) the integer-literal fast path (`e.value === (e.value|0)`) is bounds-safe against real i32 range, while the checker's `NumRange.integer` flag (see [[tison_checker_narrowing_plan]]) was NOT bounds-checked at all — a literal like `5000000000` is "integer" but doesn't fit i32.

That surfaced a real, separate pessimization the user flagged: `emitAs(literalNumberExpr, ctx, 'f64')` always emitted `i32.const` then `f64.convert_i32_s`, even though the caller already knows it wants `f64`. Fixed by threading an optional `want` hint into `emitExpr` (from `emitAs`, propagated through the two pure pass-through cases `'as'` and postfix `'!'`); the literal-number case now emits `f64.const` directly when `want === 'f64'`. `return 5;` now compiles to one `f64.const 5` instead of `i32.const 5` + convert. The return value itself stays — still needed for the two reasons above — this only removes the wasted round-trip when the physical choice was arbitrary anyway.

Two follow-on fixes at the user's direction:
1. **`wasmTypeOf`'s range→WasmType mapping now bounds-checks min/max against real i32 range** (`-0x80000000..0x7fffffff`), not just the `integer` flag — was the mechanism-level version of counter-example (2) above.
2. **`0/0` divide-by-zero trap fixed at the root, not patched**: `/`'s `builtins` entry no longer uses `arithInline`'s per-operand-kind dispatch at all — real JS `number` division is *always* float division (truncating `i32.div_s` is flatly wrong for e.g. `7/2`, not just an overflow risk like `+`/`-`/`*` sharing i32 have), so it now hard-codes `{params: ['f64','f64'], result: 'f64', inline: [f64.div]}` unconditionally (bigint division still routes separately via `bigintAware`). Combined with the `want`-hint fix above, a literal `0` operand now emits `f64.const 0` directly — never produces an i32 zero to trap on. Verified: `0/0` now correctly yields `NaN`, full suite back to green up to the next (unrelated, pre-existing) issue.
   - Flagged but NOT fixed: `%` (mod) has the same operand-kind dispatch via `__towasm_mod`'s `$T`-switch, and integer `rem_s` *does* trap on a zero divisor too — but unlike `/`, `i32.rem_s` on in-range operands is otherwise semantically identical to JS `%` (both truncate toward zero), so this is a much narrower divisor-only edge case, not a blanket-wrong operation. Left alone, not asked for.

3. **Pursued the Uint8Array/Int32Array/Uint32Array range-typing** (checker.ts): replaced the flat `TYPED_ARRAYS` name-only `Set` with `TYPED_ARRAY_RANGES: Record<string, T.NumRange>` (real bounds: Uint8Array 0..255, Int32Array -2^31..2^31-1, Uint32Array 0..2^32-1), and `case 'index'`'s typed-array branch now returns `T.rangeToType(...)` instead of plain `T.NUMBER`. This makes `wtypeOf` agree with physical reality for typed-array *reads* — confirmed `a[0] + 1` on a `Uint8Array` now stays in real `i32` arithmetic end-to-end instead of round-tripping through f64 immediately after the read.
   - Regression caught by the test suite and fixed forward (see [[feedback_fix_forward_not_revert]]): the same narrowed type was also reaching *assignment-target* checking (`a[0] = value`), wrongly rejecting real JS's "any number, silently truncated/wrapped, never a type error" typed-array write semantics (e.g. the existing "Uint8Array write of NaN/huge value no longer traps" test). Real TS itself doesn't narrow typed-array element types at all, for exactly this get/set asymmetry reason. Fixed by widening back to `T.NUMBER` specifically in the assignment-target-type override block (`case 'binary'`'s `e.operator.endsWith('=')` handling, alongside the existing `'member'` override) — read narrows, write doesn't.
   - The user's suggestion to fold lib.d.ts's `i32`/`i64`/`f32`/`f64` "dummy" pseudo-types (`declare type i32 = number` etc., used only as signal names for `__asm<P,R>` signatures, never resolved by the general checker per its own comment) into real `RangeType`s was NOT pursued this round — `RangeType` has no TS surface syntax, so it'd mean special-casing these specific ref-type *names* somewhere in general type resolution (`T.resolve` or similar), which is a different, currently-unexplored mechanism, not just a data change. Left as a next-step idea, not attempted.

**Newly exposed, NOT fixed**: suite now runs further and stops at `towasm: call to unknown function 'reducePi2'` (a top-level `const reducePi2 = (x: number) => {...}` in `lib/number.ts`, called from `Math.sin`/`Math.cos`) — looks like top-level arrow-function consts used as free-standing callable functions aren't resolved the same way `function` declarations are. Not investigated, flagged only.
