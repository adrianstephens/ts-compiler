`examples/ts-codegen.ts` converts tison parser ASTs (`TSProgram`/`TSStatement`/`TSType`/`Expr`) back to source code via `tsToCode(ast, opts?)`. Covers all TSType variants, TSDeclaration types, ambient (`declare`) statements, TS expressions (`as`/`satisfies`/non-null), and every JS statement/expression from js-parser.ts. Round-trip verified against the real-workspace corpus in [[tison_project]]'s gap-fixing loop (`test/test-ts-parser.ts`: parse → tsToCode → reparse). `CODEGEN.md`/`test-codegen.ts` mentioned in an earlier version of this memory no longer exist — don't look for them.

**JS-output mode added 2026-07-03:** `tsToCode(ast, { js: true })` emits plain JavaScript instead of TypeScript — strips type annotations/params, `as`/`satisfies`/non-null unwrap to their inner expression, `interface`/`type`/`declare`/bodyless-overload-signatures are erased entirely (filtered from statement/class-member lists so no stray blank lines), `enum` becomes a plain `const` object literal (numeric members auto-increment, loses tsc's reverse `Enum[0] === "Name"` mapping — documented simplification), and constructor parameter properties (`constructor(public x: number)`) expand into a plain parameter plus a synthesized `this.x = x;` statement prepended to the constructor body, matching real `tsc`'s transpile.

**Implementation is module-scoped state (`let jsMode`), not a threaded parameter** — deliberate choice: threading an options object through the ~25 mutually-recursive codegen functions risks a forgotten forward silently leaking TS syntax mid-subtree; module state is safe here because a `tsToCode` call is a single synchronous call stack with no reentrancy into `tsToCode` itself. `jsMode` is set unconditionally at the top of every `tsToCode` call (no save/restore — every call fully determines it from its own `opts`).

**Verification method for any future ts-codegen.ts change:** (1) typecheck + eslint on the file; (2) diff `tsToCode(ast)` (default/TS mode) against a pre-change copy of the file across the 8-file real-corpus (same files used in [[tison_project]]'s perf work) — must be byte-identical, since TS-mode output must never regress; (3) construct a small TS snippet covering the new feature's cases, run both modes, eyeball; (4) for JS-mode specifically, write the generated JS to a temp file and execute it with plain `node` (no ts-node) to confirm it's real, runnable, correct JS — caught nothing this session but is the only way to be sure generated JS isn't just syntactically plausible.

**`TStoDecl(ast: TSProgram): TSProgram` — `.d.ts`-generation AST transform, implemented and fully verified 2026-07-03/04 (exported, ~350 lines, placed right after `TStoJS`).** Design question that preceded it: user asked whether a visitor pattern would help unify `TStoJS`/`TStoDecl`/future transforms — answered no (not implemented as one): `TStoJS` needs a deep expression walk since runtime code can appear anywhere, while `TStoDecl` is fundamentally shallower (signature-extraction plus a type-level-only reachability walk), so a shared visitor would force the shallow case to pay for machinery it doesn't need. Both remain independent closures-in-a-function, matching the file's existing style.

**Two-phase design: (1) reachability (what survives), (2) strip/rebuild (how each surviving decl loses its runtime parts).** Phase 1 does a mark-and-sweep/BFS from explicitly-exported roots, chasing only *type-level* references — this matches real `tsc --declaration` behavior (an exported signature pulls in a non-exported interface/class it mentions, but never pulls in a purely-internal helper *function* merely called from a now-discarded body). **Key clarification the user gave mid-implementation** (system-injected, not a normal chat turn): types needed by exported types must be detected even when not directly exported themselves — this is what makes it a transitive-closure BFS rather than a single-hop "is it exported" filter.

Phase 1 machinery: `addRef`/`collectParamRefs`/`collectTypeParamRefs`/`collectTypeMemberRefs`/`collectTypeRefs` (exhaustive `TSType` switch walking every type-position for identifier references) plus `collectValueRefs` (walks a class's `extends` clause specifically, since that's an `Expr` not a `TSType`). `owners: Map<string, Owner[]>` maps each top-level bound name to the statement(s) that declare it (`interface Owner { stmt: TSStatement; declarator?: VarDeclarator }`, since a `var` statement can bind several names in one statement). `roots: Set<string>` seeded from `export_decl`/bare `export {name}` (no source)/an `export default someIdentifier;` second pass. **Deliberate, documented simplification: `interface`/`type`/`enum` declarations are always treated as roots** (i.e. always kept, whether referenced or not) — the AST has no reliable way to tell whether an unexported one is truly dead vs. merely not yet referenced by something also being kept, and false-negative pruning (dropping something actually needed) is worse than false-positive keeping (an unused type surviving) for a declaration file. BFS worklist (`collectDeclRefs`/`collectMemberRefs`) grows `reachable: Set<string>` from the roots.

Phase 2 machinery mirrors real `.d.ts` semantics point for point: `inferType(e, narrow)` — `const` infers the narrow/literal type (`5` → literal `5`), `let`/`var` widen (`WIDEN` map: `number`/`string`/`boolean` primitives); `as T` gives static type `T` directly (`e.typeAnnotation`); `satisfies T` preserves the *expression's own* inferred type, not `T` (recurses into `inferType(e.expression, narrow)`); function/arrow expressions infer a `{type:'function', params, returnType}` TSType shape. `stripParam` fills in a missing `typeAnnotation` from `inferType(p.default, false)` when there's a default, then drops the default itself (ambient declarations can't carry runtime default values — a defaulted param becomes optional-but-typed instead). `stripFunctionDecl` clears `body`/`async`/`generator` (all three are implementation-only, never valid on a bodyless ambient signature — `async`/`generator` erasure was a follow-up fix once the corpus scan surfaced `export declare async function`, since `async` markers are meaningless on a signature with no body to run). `stripVarDeclarator` returns `VarDeclarator[]` (not a single declarator) so a destructured top-level export (`export const {a,b} = obj;`) can be split into individual simple declarators (`declare const a: any; declare const b: any;`) — ambient declarations have no initializer to destructure against, so the only valid shape is one simple binding per name, each typed `any` since there's no annotation to recover the real per-field type from.

**Class member handling — the one place a full grammar fix was deliberately avoided in favor of an AST-level workaround, documented as a known gap:** `TSClassMember`'s `method_signature` variant has no `kind` field, so it structurally cannot represent a bodyless `get`/`set` accessor signature, and no dedicated grammar shape for one was ever added (a third risky grammar change was judged not worth it after the `static`+overloads fight — see [[tison_project]]). Instead `stripClassMember` converts `get`/`set` methods to plain `field` entries (typed from the getter's return type or setter's param type), and a `mergeAccessorFields` pass in `stripClassDecl` merges a get+set pair sharing one string key into a single field — `readonly` only when a getter exists with no matching setter, plain mutable otherwise; **computed keys are NOT deduplicated** (acknowledged minor gap — a computed get/set pair would emit two separate fields instead of merging, though this is a narrow edge case not hit anywhere in the real-workspace corpus). Verified directly with 3 targeted repros (get-only→readonly field, get+set→merged mutable field, set-only→mutable field) — all reparse correctly.

**`export default` handling needed 4 sub-cases, not the 1–2 you'd guess from the grammar alone — found by direct AST inspection, not assumption:** `export default identifier;` (root the identifier, re-emit as-is once it's confirmed reachable), `export default function name() {...}` (asymmetric vs. `class` in this grammar — a *named* function default parses as a plain `{type:'function',...}` Expr, not a `function_decl` Statement, the way `class` correctly does; had to detect this and manually reconstruct a `function_decl`-shaped node before stripping), `export default class Name {...}` (already a `class_decl`, straightforward), and `export default {a:1, ...};`/other anonymous expressions (no name to hang a declaration on — synthesizes `const _default: T; export default _default;` using `inferType` on the expression).

Root-caused with real evidence (traced `isAssignable`'s full recursive call tree via a temporary wrapper logging every FALSE result with depth+src/dst — reasoning from the code alone repeatedly gave a plausible-but-wrong story first, per [[tison_debugging_technique]]'s general lesson). Actual mechanism: `Expr` (js-parser.ts) is a large self-referential union whose own members' properties reference `Expr` again (e.g. `elements: readonly (Expr|undefined)[]`); `isAssignable`'s only fast path for such cycles is reference-equality (`dst.types.some(t => t === src || ...)`) between a union member and the value being tested. But `resolve()`'s generic-ref branch calls `substituteType(entry.type, new Map(...))` on **every** call, even for a bare reference with no explicit type args (`Function`, not `Function<T>`) — `substituteType` walks via `TSwalk` and always returns a **freshly cloned** tree, so two independent resolutions of the same bare generic ref (e.g. `Function`, itself `{...} & ParamListReturn<T>`, one of `Expr`'s members) are structurally identical but never `===`. That reference inequality defeats the cycle-breaking fast path specifically for any `Expr` member that is itself a generic type alias referenced bare (`Function`, `Arrow` — both have `T = unknown` defaults) — the `.every()` over `Expr`'s 24 members then genuinely fails on that one member, failing the whole union comparison, cascading up through `readonly`/`parenthesized`/`ref` wrappers to the top-level "not assignable" verdict. Two-part fix: (1) `resolve()` now caches the default-args substitution per `TypeEntry` object (`defaultSubstitutionCache: Map<TypeEntry, Type>`) so every bare-generic-ref resolution of the same entry returns the *same* cached object — only applies when `t.typeArgs` is absent (explicit-args resolutions are unaffected, still fresh each time); (2) `isAssignable` gained a cheap `if (src === dst) return true;` right after both sides resolve, both a safety net and a genuine optimization once (1) makes same-node convergence common. Verified: `TStypeCheck` on `js-parser.ts` alone went 1→0 diagnostics; full monorepo `test-ts-parser.ts` sweep (`testDir`, the one that previously crashed on an unrelated `ModuleLoader`/`fs/promises` bug before ever reaching this file — see [[tison_project]]'s 2026-07-09 `.d.ts`-parsing entry) now completes end-to-end with **zero parse failures and zero type diagnostics across the entire workspace**. `tsc --noEmit` clean, no new errors.

**`ModuleLoader` rewritten 2026-07-09 to do real Node/TS module resolution instead of a single `node_modules/<mod>.d.ts` guess.** Old `get(mod)` only tried `path.join(nm, mod) + '.d.ts'` per `node_modules` dir — never looked in `@types/`, never handled subpaths (`fs/promises`), never stripped a `node:` prefix, and never consulted a package's own `package.json` "types"/"typings" field. Separately, the constructor's eager `@types` pre-scan had a real bug: `const types = path.join(nm, '@types')` **shadowed** the constructor's own `types?: string[]` restriction parameter, so `types.includes(i.name)` was checking `String.prototype.includes` (does the `@types` directory *path string* contain the package name as a substring?) instead of the intended array membership check — it only "worked" for `'node'` by luck, since `"node_modules"` itself contains the substring `"node"`. Fixes: (1) renamed the shadowing local to `typesDir`, restriction param to `restrictTypes`; (2) `get()` now splits a bare specifier into `{pkg, subpath}` (`splitSpecifier`, scope-aware for `@scope/pkg/...`), tries the package's own bundled types first (via its `package.json` "types"/"typings", `ownTypesEntry`) then the DefinitelyTyped `@types/<mangled-pkg>` package (`typesDirName` mangles `@scope/pkg` → `scope__pkg`), each via a `tryLoad(base, rel)` helper that tries `rel.d.ts` then `rel/index.d.ts`; (3) any file found this way is scanned for `declare module "X" {...}` wrappers (`registerDeclaredModules`, shared with the eager scan) since a single `@types/node` file routinely backs *several* specifiers at once (`fs/promises.d.ts` declares both `"fs/promises"` and `"node:fs/promises"`, the latter often just a 1-statement `export * from "fs/promises"` re-export alias) — a file with no wrapper is a plain external module whose own top-level statements directly are the exports. **Real bug caught only by testing, not by reading the diff — and NOT a race condition, despite my first description of it as one (user correctly pushed back on that word):** the first version checked `this.imported` for a cache hit only *before* `await this.node_modules`. `await this.node_modules` genuinely, deterministically waits for the constructor's entire eager `@types` scan to finish (confirmed directly: `this.imported.has('fs/promises')` is `true` immediately after that await, every time) — there's no timing-dependent nondeterminism here. The bug was simpler and 100%-reproducible: the pre-await check is pointless (the scan hasn't run at all yet on the very first call), and after the await the code never re-consulted `imported` before falling through to file-path resolution — so for any specifier the scan alone can find (a node-builtin subpath like `fs/promises`, keyed only by its `declare module` wrapper, never by a matching file-path), it deterministically got a false "not found" from the (wrong, for this shape) file-path fallback and **overwrote the correct value the scan had just set**. Final fix (after first trying "recheck the cache again after the await", then simplifying once the user asked "why not just await unconditionally up front") — moved the single `await this.node_modules` to the very top of `get()`, before any cache check at all; one await, one set of checks, no dual-check duplication. Lesson: the two-tier "check, maybe-await, check-again" pattern is itself the kind of premature optimization (saving one microtask tick on an already-cached hit) that caused this bug — awaiting unconditionally first is both simpler and strictly safer here since `node_modules` (the array) is needed by every non-cached path anyway. Also: `tryLoad` used to swallow a genuine *parse* failure (file found, but this grammar can't parse it — e.g. the real `typescript` npm package's own 590KB `lib/typescript.d.ts`) in the same catch as "no such file", silently misreporting it as unresolved; split into a file-read try (silent, expected to miss on most candidates) and a separate parse try that `console.error`s like `loadTypes` already does, so a real grammar gap on a found file stays visible instead of masquerading as a missing package. Verified against the real workspace `node_modules` (`fs/promises`/`node:fs/promises`/`fs`/`path`/`os` all resolve correctly with proper statement counts; `estree`/`json-schema` bare `@types` packages resolve; `typescript` correctly logs a parse failure instead of silently returning nothing) and via the full `test-ts-parser.ts` corpus sweep (still 0 diagnostics, no crash, two new log lines for the `typescript` compiler's own `.d.ts` and `@vscode/debugprotocol`'s `.d.ts` — both genuine out-of-scope grammar gaps on advanced/generated files, not resolution bugs).

**`Function`/`Arrow`/`FunctionDecl`/`Param`/`ClassMember`'s `async`/`generator`/`optional` boolean fields folded into a shared `modifiers: string[]` tag list, 2026-07-09 — motivated by wanting the core js-parser.ts AST shapes reusable across non-JS-language grammars, not just JS/TS.** User's framing: `modifiers` should hold *semantic tags* (`'async'`, `'generator'`, `'optional'`), not literal source keywords — a renderer maps each tag back to whatever syntax its own language uses (prefix keyword, suffix `?`, `*` infix, whatever), so the shared AST layer stays syntax-agnostic. Expression-level `optional` (the `?.` on `member`/`index`/`call` — an *operator* on an expression, not a declaration modifier) deliberately stayed a plain boolean; only *declaration*-level flags moved. `js-parser.ts` gained a shared `toParam(binding, extraModifiers?)` helper (folds `optional_binding_name`'s bare `optional` flag into `Param.modifiers`, used both in its own `parameter` rules and reused by `ts-parser.ts`'s parameter-property rules to merge with `public`/`private`/`readonly`). Renderers (`paramListToCode`, `classMemberToCode`, function/arrow `exprToCodeBody`) now filter `'optional'`/`'async'`/`'generator'` out of the plain-keyword-join and render them specially (trailing `?`, prefix `async `, infix `*`) — also fixed a latent pre-existing gap found while touching this code: class *method* rendering never emitted `async ` at all (only `generator`'s `*`), so async class methods never round-tripped through `TStoDecl`/`tsToCode` correctly even before this refactor.

**Two real "parameter-property detection" bugs surfaced by the refactor, both the same shape: code that used `p.modifiers?.length` as a proxy for "this param has an accessibility modifier, so it's a constructor parameter property" started false-positive-ing on a merely-*optional* (but not `public`/`private`/etc.) param, since `'optional'` now also lives in the same array.** Sites: `TStoJS`'s constructor-prelude synthesis (`fn.params.filter(p => !!p.modifiers?.length)`) and `classShapes`'s constructor-property member synthesis (`ts-codegen.ts`). General lesson: any code checking "does this modifiers array have anything in it" as a stand-in for a *specific* modifier's presence needs re-auditing after this refactor, since the array's population grew wider than the check anticipated.

**Genuine remaining gap, found but deliberately NOT fixed this session (documented, not silently left as a mystery): eager class-method-body checking vs. lazy forward-referenced `namespace X {} + const X = ...` declaration-merging.** Real pattern (seen in `maths/src/vector.ts`): a class `_float2` declared *earlier* in a file has methods that call `float2(...)` — a `const float2 = Object.assign(fn, {...statics})` declared *later* in the same file, declaration-merged with an earlier `namespace float2 { export type extent = ...; }`. Real TypeScript allows this (class method bodies aren't evaluated until call time, well after the whole module finishes initializing). This checker's `checkClassMembers`/`checkFunctionBody` checks class method bodies *eagerly*, in file order, as part of the single sequential `checkBlock` walk — unlike top-level function return types, which already have dedicated lazy-inference machinery (`fnBodies`/`inferReturn`/`callReturn`). Compounding factor: `hoist`'s `namespace_decl` case eagerly pre-populates `scope.values` with the namespace's own (here, empty — its only export is a type alias) object shape *before* the sequential walk ever reaches the real `const` — so the early class's methods, checked before that point, see a stale empty-object placeholder and incorrectly report "Type '{}' is not callable" instead of either correctly seeing the merged type or at least staying lenient (ANY). Root-caused via direct instrumentation (`console.error` at the exact "not callable" call site, run against the real failing file — two prior hand-written repros attempting to reproduce the same shape both surfaced 0 diagnostics, underscoring that guessing at a minimal repro from reasoning alone is unreliable here; only reproducing from the real file's actual statement order/content worked). Proper fix would mean deferring class method body checks to a second pass (after the whole file's hoisting *and* top-level `var`/`const` sequential evaluation) — a real architectural change to `checkBlock`'s single-pass sequencing, out of scope for a diagnostic-cleanup pass. Affects at least `maths/src/vector.ts`/`vector`'s own sync test (~61 diagnostics each) and cascades into `maths/tests/test-vec.ts` (87) and similar.
