## What TStoDecl (transform.ts) now does, beyond the earlier declScope/cross-module-ref work in [[tison_project]]

Added `resolveTypes(entryScope, importScope)` — the `onType` callback driving `TStoDecl`'s final print walk. Two things it does that plain declScope-qualification didn't:

1. **Structural resolution of nameless constructs** (`mapped`/`conditional`/`indexed_access`/`keyof`/`typeof`) via `T.resolve(scope, type, undefined, stopAtRef=true)` — added a `stopAtRef` param to `T.resolve` itself (type-utils.ts), defaulting `false` (zero behavior change for every other caller — isAssignable, member lookup, etc.). When `true`, the `ref` case short-circuits instead of expanding, so resolution stops at the first named type it lands on rather than always drilling to full structure. Only `resolveTypes`'s printing pass ever passes `true`.
2. **Un-inlining refs whose own declared body is itself resolvable** (e.g. `bin.ReadType<T>`, a conditional type — real TS doesn't give conditional-type results a stable alias identity either, so unwrapping it isn't a readability regression the way flattening a plain interface would be). Plain named refs (interfaces/classes/ordinary type aliases) are still left as names.
3. **`findDeclaredName`**: after a resolve produces a structural result, reference-identity-checks it (`Scope.findDeclaredName`, walking `.parent`, checking each scope's *own* type map) against every declared type in scope — if the resolved shape literally *is* some class/interface's own registered type (e.g. `infer R` binding to a class reference's instance type via generic inference, with no name attached along the way), prints that name instead of the raw structure.
4. **`bin.Class(spec)`-as-heritage hoisting**: a class `extends` clause that's a call expression can't survive into ambient `.d.ts` output. `stripClassDecl` synthesizes `declare const Foo_base: <computed type>` ahead of the class and rewrites `extends` to reference it — same trick real tsc's declaration emitter uses. After a later refactor (single strip-pass, `stripClassDecl` only runs once per class — see [[tison_project]]/session notes on that refactor), the synthesized bases are prepended into the tree *before* the single print walk, so the same `onType` pass resolves their types too — no separate nested walk call needed.
5. **Enum/union-literal constrained-generic overload expansion** (`expandConstrainedGeneric`): `f<T extends "A"|"B">(x: T): R<T>` → one non-generic overload per literal member, each with `R`'s value resolved for that specific member. Motivated by wanting `ReadDirectory(name: "IAT"): MappedMemory` instead of one generic signature dragging in the whole `DIRECTORIES` lookup table.

## Round 1 bugs (printer-side, all still valid)

1. **walker.ts tuple `elements`**: used `mapArray` (collapses empty array → `undefined`) instead of `mapArrayA` for the mandatory field — crashed the printer whenever resolution produced a genuinely empty tuple `[]`. Same bug class as an earlier class/interface-body fix — check `mapArray` vs `mapArrayA` first whenever a "mandatory but can legitimately be empty" array field crashes the printer.
2. **`matchInfer`'s object-pattern case** only handled `property`-kind members — a `{new(s:any): infer R}` pattern's `construct`-kind member was silently skipped, so the match always vacuously succeeded with `R` unbound, leaking a bare dangling `R` name into printed output. Fixed to handle `call`/`construct` members, including when `a` itself is a bare `constructor`/`function` type (not wrapped in an object literal).
3. **Cycle-guard catch scope** (transform.ts, `resolveTypes`): the `ComputedCycle` bail-exception try/catch only wrapped the `RESOLVABLE` branch, not the sibling foreign/unreachable-ref inline branch — a cycle thrown from deep inside *that* branch had nothing to catch it and crashed the whole run. Fixed by wrapping both branches in one try/catch keyed off one `topLevel` flag.
4. **Object-literal spread type inference** (checker.ts `case 'object'`) deliberately bailed to `any` on any spread property (`{...X, key: y}`) — pre-existing, documented ("spread makes the shape unknowable here"). Fixed to actually resolve the spread operand and merge its members in (later members override earlier ones by key) — falls back to the old `any` bail only if the spread operand doesn't resolve to a determinable object shape.
5. **Cycle-guard keyed by alias only, not (alias, argument)**: a generic alias like `ReadType<T>` legitimately re-enters itself once per nested field with a *different* `T` — that's ordinary finite recursion, not a cycle. Fixed by keying on `(entry.type, typeArgs[0])`. This exposed a **second** bug: with no false-positive to accidentally bound it, resolution stack-overflowed for real, so a separate depth cap (`MAX_DEPTH = 40`, a plain nesting counter) was added alongside it.

## Round 2 bugs (found by pushing past the round-1 "dead end" — this is the important correction)

An earlier version of this memory concluded the remaining `bin.ReadType`-over-real-specs bailing was a *confirmed architectural dead end* needing "structural equality or type interning" — **that conclusion was wrong, or at least premature.** The user asked to keep pushing given the context already built up, and it paid off. What was actually true: reference-identity cycle detection genuinely couldn't see the repeat, but the reason wasn't that a real cycle was hiding from it — it was that resolution was taking a **wrong path** due to real, fixable bugs, and what looked like "infinite distinct instantiations" was actually a symptom of those bugs, not genuine unbounded recursion. Switching the cycle-guard key to `T.typeKey` (structural/printed-code string equality instead of object identity) was tried and changed *nothing* — further proof the problem was never about cycle detection at all.

The actual chain, root-caused by tracing (not guessing) with targeted `console.error` instrumentation at each suspect layer:

1. **`isAssignable`'s "unresolved named type: be lenient" fallback** (type-utils.ts, `dst.type === 'ref'` branch) didn't distinguish a genuinely-unresolvable generic/import ref from the well-known `Array`/`ReadonlyArray` refs (neither is in `ALL_PRIMITIVES`, so both got the same "be lenient" treatment). This let *any* plain object wrongly "extend `readonly unknown[]`", misrouting `ReadType<T>` into its `TupleReadType` branch for non-array specs. Verified directly: before the fix, 129/129 of these checks wrongly returned `true`; after, all correctly `false`. Fix: explicit `if (dst.name === 'Array' || dst.name === 'ReadonlyArray') return false;` before the lenient fallback.
2. **This fix alone wasn't enough** — `ReadType<First>` (with `First`/`Rest` literally the raw, unbound `infer` names from `TupleReadType`'s own declaration) kept leaking into output regardless. Traced via stack traces and targeted dumps (not assumption) to the *real* cause: `ReadType<T>`'s own `T extends readonly unknown[]` check was being evaluated with `T` **still abstract** — not the concrete field type. Why: `NonMerged<T>`'s per-field mapped type is `{[K in keyof T as <condition>]: ReadType<T[K]>}` — an **`as`-clause key-remapping mapped type**. `resolve()`'s `'mapped'` case had an explicit, documented, intentional gap: `if (!t.nameType) {...} break;` — any mapped type with an `as` clause was never resolved at all, just returned verbatim, `K` and all unsubstituted. That raw `ReadType<T[K]>` (with literal `K` never bound) is what got walked and printed. Fixed by implementing real `as`-clause support: for each candidate key, resolve the `nameType` expression with that key substituted in; skip the key if the result is `never`, use it as the output key if it resolves to a string/number literal, and — matching this function's existing "never guess" philosophy — bail the *entire* mapped type back to opaque if any single candidate's output key can't be determined.
3. **Fixing #2 alone caused a real corpus regression** (`ERROR` 18→38, all `bin.Expect(spec, "literal")`-shaped) — since `NonMerged` now actually evaluates instead of staying opaque (and opaque/`OPAQUE` types are checked leniently elsewhere), a **second, pre-existing, previously-masked bug** in `matchInfer` got exposed: `{get: (s:any) => infer R}` against `get<T> = ((s:sync)=>T) & ((s:async)=>Promise<T>)` — a genuine **intersection of two function overloads** — failed outright on `a.type !== pattern.type` (intersection ≠ function) before ever trying either overload. Fixed by trying each intersection member: `a.type === 'intersection' ? a.types.some(m => matchInfer(pattern, m, ...) === true) : ...`. This restored `ERROR` to the 18 baseline.
4. **Bonus (cosmetic, not correctness)**: `matchInfer`'s ref-with-typeArgs case returned `undefined` ("can't confidently decide") whenever the actual type's ref-name didn't match the pattern's — even for a resolved *primitive* (`string`/`number`/etc), which can never structurally satisfy any generic ref pattern like `PromiseLike<infer R>`. This left redundant `T extends PromiseLike<infer R> ? R : T` wrappers in output for primitive fields. Fixed: `isPrimitive(a) ? false : undefined`. Left object-typed fields' residual `PromiseLike` wrapper alone (didn't broaden the fix to `'object'` kinds) since an object *could* theoretically be a real thenable — the primitive case is unambiguous, the object case isn't.

## Round 3 — PE_base fixed too (the "still bails" case below is now closed)

`resolve()`'s `case 'mapped'` only ever resolved `t.constraint` directly. `DiscrimSwitch<KName,T>`'s constraint is `keyof T & (string | number)` — an **intersection**, and `resolve()` had (and, at the top level, still has) no case for `'intersection'` at all. So `constraint` stayed unresolved, the mapped type's key variable never got bound, and the unbound `ReadType<T[J]>` leaked out — the same "bare infer name" symptom as the round-2 bugs, but from a different upstream cause. Fixed by splitting `t.constraint` into intersection members when present (`constraintParts = t.constraint.type === 'intersection' ? t.constraint.types : [t.constraint]`), resolving each, and using whichever member reduces to a literal/union-of-literals as the effective constraint; the homomorphic-`keyof` detection was likewise changed from `t.constraint.type === 'keyof'` to `constraintParts.find(m => m.type === 'keyof')?.argument`.

Verified: cycle-guard "First" (unbound infer name) trigger count dropped from ~18 to 1; corpus `ERROR` held at 18 (no regression); direct inspection of `pe.debug.d.ts` shows `PE_base`'s `opt` field's `CorrelatedMerge<DiscrimSwitch<...>>` now fully spells out each of the 6 real discriminant variants (NT32/NT64/ROM/OBJ/TARGET/HOST) with their own distinct concrete fields, instead of bailing to raw `bin.ReadType<{...spec...}>`.

## Actual current outcome

`Section_base`, `COFF_base`, `COFFSymbol_base`, `RESOURCE_DATA_ENTRY_base`, and now **`PE_base`** (plus `DOS_HEADER`/`EXE_HEADER`) in `pe.debug.d.ts` all **fully resolve** to their real computed shapes instead of bailing to raw `bin.ReadType<{...spec...}>`. The only remaining `bin.ReadType<...>` in the file is a legitimate top-level `type Directory = bin.ReadType<{...}>` alias, not a bail.

**Known, deliberately-not-fixed cosmetic residue**: object-typed (non-primitive) fields still show a redundant `X extends PromiseLike<infer R> ? R : X` wrapper around their own concrete type (e.g. `AddressOfEntryPoint: {value...} extends PromiseLike<infer R> ? R : {value...}`) — this is the documented round-2 bug #4 decision (`isPrimitive(a) ? false : undefined` in `matchInfer`'s ref case), deliberately left alone for object types since an object could theoretically be a real thenable. Not a regression, not new; just still there and still verbose-but-correct.

This closes the investigation from the "given the context you've built up so far I think it's worth exploring further" push — there is no more known bailing case in `pe.debug.d.ts`.

## Known remaining issue: `opt`'s spurious `_` key (investigated, root-caused, fix NOT applied — too risky)

The user noticed real tsc's own `pe.d.ts` is 629 lines vs tison's 4736 — a real signal, not just "more verbose is fine". Investigated and found a genuine bug: `PE`'s spec has a field literally named `_: bin.Switch('Magic', {...})` (the discriminant-switch marker key, per `binary/src/types.ts`'s convention). `ReadType<T>`'s `NonMerged<T>` mapped type is supposed to **drop** this key (`T[K] extends {new(...):any} ? K : T[K] extends {get:...}=>infer R ? (NoPromise<R> extends MergeBase<any> ? never : K) : K`) and let `AllCorrelated<T>` splice its members in via intersection instead — but tison's checker keeps `_` as a literal nested property (`_: bin.CorrelatedMerge<{NT32:...,NT64:...}>`), which is wrong and roughly doubles output size on top of (via a separate, unrelated `X extends PromiseLike<infer R> ? R : X` residue-wrapper pattern for every object-typed field) duplicating the whole resolved shape.

Root cause, traced (not guessed) via targeted instrumentation: `isAssignable`'s `dst.type==='object'` structural check has `if (m.type !== 'property' ...) return true; // methods/call/index/computed: lenient` — a **blanket lenient pass for `call`/`construct`-kind dst members**, so `T["_"] extends {new(...args:any):any}` (meant to detect "is this a constructible/class spec") always vacuously returns `true` for *every* field, taking the trivial `K`-keep branch immediately and never reaching the `{get:...}`-based drop-if-correlated check at all — for `_` or anything else.

Fixing that leniency (make `call`/`construct` dst members real checks) is necessary but **not sufficient on its own** — it unmasks a *second*, much more load-bearing pre-existing leniency: the same function's absent-property fallback `hasMod(m,'optional') || !sealed(src,scope) || recurse(UNDEFINED, m.typeAnnotation, depth-1)` lets a **required property typed `any` vacuously pass even when genuinely absent** (`recurse(undefined, any)` is trivially true) — e.g. `NoPromise(R) extends MergeBase<any>` (checking only `merge: any`) is `true` for *any* `R` regardless of whether `R` actually has a `merge` field, since real TS would require the key to literally exist and this doesn't. Removing that leniency term is what real TS semantics call for, but caused a **severe regression**: `Section_base`/`COFF_base`/`DOS_HEADER`/etc. (all previously correctly fully-resolved, per the round-1/round-2/round-3 fixes above) started **losing real fields** (`Name`, `PointerToRawData`, `Characteristics`, `res`, `res2`, `Machine`, and the entire `opt` field vanished) — some *other*, not-yet-identified consumer of this exact leniency is load-bearing for currently-correct behavior elsewhere in the `ReadType`/`NonMerged`/`AllMerged`/`MergeResult` pipeline.

Separately, even with both `isAssignable` fixes applied, a **third**, independent gap surfaced in `binary-archives/src/zip.ts`: `ZIPheader = Pick<bin.ReadType<typeof file_header>, ...> & {...}` — `atime`/`ctime`/`uid`/`gid` (only present in *some* branches of a nested `extra` discriminated-union merge, hence genuinely optional in real TS via `MergeResult<A,B>`'s `[K in Exclude<keyof B,keyof A> as undefined extends B[K] ? K : never]?: B[K]` clause) came out non-optional in tison's resolution, causing 2 new corpus `ERR`s. A speculative fix (inferring `Pick`'s per-key modifiers from the source object even when the constraint isn't literally `keyof T`, via `valueType`'s `T[P]` shape instead) was tried and had **zero effect** on this or anything else in the corpus — reverted as unverified scope creep.

**Decision: reverted both `isAssignable` changes.** The `_`-key/size issue is real and root-caused, but a safe fix requires first finding what relies on the any-absorbs-absent-property leniency (the second bug) before it can be removed without regressing already-correct, already-hard-won output. This needs its own dedicated investigation (same rigor as the rounds above — trace what specifically breaks when that leniency is removed, field by field) before attempting again. Current state (`_` key present, ~4736 lines) is a known, understood, accepted trade-off, not a fresh gap — don't re-attempt this without budgeting for a full investigation, and don't just re-apply the two `isAssignable` changes from this note without also solving the regression they cause.

Verified throughout: type-checks clean (`npx tsc --noEmit -p examples/tsconfig.json` — note: the *root* `tsconfig.json`'s `-p .` does NOT cover `examples/`, only `src/**`; use `examples/tsconfig.json` to actually check these files), no crash, corpus `ERROR` count stable at 18, eslint clean (only pre-existing `custom/no-single-use-local` style warnings, 0 errors).

## TStoDecl's own `checkBlock` pass is load-bearing, not just redundant (2026-07-26)

Context: `TStypeCheck`/`TStypeCheckAsync` (transform.ts) already stamp their fully-checked top-level `Scope` onto `ast.scope`. `TStoDecl` separately builds *another* scope (`importScope ? new Scope(importScope) : T.makeGlobal()`) and re-runs `checker.checkBlock(ast.body, global)` on it — looked like pure redundant duplicate work (same conclusion independently reached for [[tison_project]]'s new `TStoWasm`, where removing the equivalent redundant `checkBlock` and reusing `ast.scope` directly was verified safe by its own test suite).

Tried applying the identical simplification to `TStoDecl`: drop its own `checkBlock` call, reuse `ast.scope` directly (with a throwing precondition, matching `TStoWasm`). **Verified via real corpus diff** (binary-libs' `pe.ts`, format-13 `.debug.d.ts` output, before/after) rather than reasoning abstractly — this is exactly the "trace actual output, don't assume" discipline the methodology note below already calls for. Found a real regression: `PE.ReadDirectory`'s overloaded return types collapsed from `[string, any][]` / `{[key: string]: any}` down to bare `any`. Tried preserving the parent/child `Scope` shape (`new Scope(importScope)` without the `checkBlock` call) as a middle ground — same regression, so it's specifically `checkBlock`'s own walk over `ast.body`, not the scope's shape, that overload-return-type inference for TStoDecl's un-annotated overload members (`checker.inferReturn`/`checkClassMembers`'s overload-group matching) depends on. Not yet root-caused *why* — reverted rather than dig further, since `resolveTypes`/return-type inference in this exact file is already known-fragile (see rounds 1-3 above).

**Decision: reverted.** `TStoDecl` keeps its own `checkBlock` call as before. Don't re-attempt this dedup without budgeting a real investigation into what `TStoDecl`'s private `checkBlock` pass sets up (probably something overload-group-related in `checkClassMembers`/hoisting) that a pre-stamped `ast.scope` from `TStypeCheck`/`TStypeCheckAsync` doesn't already have. `TStoWasm`'s equivalent simplification is unaffected/still valid — its subset has no classes/overloads, so it never touches this path.

## Methodology note worth repeating

Every one of the round-2 bugs was found by **instrumenting and tracing actual runtime values** (stack traces via `new Error().stack`, targeted `console.error` dumps of `check`/`t.checkType`/`t.extendsType`/etc. at each suspect layer, gated behind `env.DEBUG_*` flags and removed after), never by reasoning abstractly about what "should" be happening. Several plausible-sounding hypotheses were tested and falsified this way (the `typeKey` structural-equality idea; an initial guess that `TupleReadType` itself had the spread-matching bug, when the actual instance was legitimate but a *different*, still-abstract-T instance further downstream). Don't skip straight to a fix based on how the code "should" behave — verify what it's actually doing first.
